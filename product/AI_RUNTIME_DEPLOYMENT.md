# Delivery Clarity — Self-Hosted AI Runtime

**Status:** Canonical operational companion to `Delivery_Clarity_Soft_Launch_AI_Master_Plan_v1.1.docx`  
**Scope:** Delivery Intelligence provider runtime only

## Runtime choice

Delivery Clarity uses Ollama as the private/self-hosted model runtime. No paid cloud AI API is required by default.

Required models:

```bash
ollama pull qwen3.5:4b
ollama pull qwen3.5:9b
```

Configured defaults:

```text
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_FAST_MODEL=qwen3.5:4b
OLLAMA_DEEP_MODEL=qwen3.5:9b
```

## Model responsibilities

| Model | Delivery Intelligence use |
|---|---|
| `qwen3.5:4b` | Flow & Bottleneck and Risk & Quality; fast/focused evidence review |
| `qwen3.5:9b` | Executive Briefing and Forecast; deeper cross-signal synthesis |

Executive and Forecast retry with the fast 4b model when the 9b model is unavailable. If no configured model can answer safely, the app falls back to deterministic Evidence mode.

## Security boundary

Ollama is server-side infrastructure. It must never be exposed directly to a browser or the public internet.

Preferred deployment shapes:

1. Ollama on the same private host as the Node application, bound to localhost; or
2. Ollama on a separate private inference host reachable only from the Delivery Clarity application network.

`OLLAMA_BASE_URL` is read from the server environment only. The browser cannot choose or override the provider URL or model.

Do not put credentials in the URL. The application accepts only `http:` or `https:` Ollama base URLs and falls back to localhost for malformed, unsupported, or credential-bearing URLs.

## Data boundary

The interactive Delivery Intelligence endpoint sends a compact evidence snapshot, not the original Jira CSV/XLS/XLSX export.

Current snapshot coverage includes headline delivery metrics, ranked risk items, selected capacity hotspots, selected epic signals, forecast values, data-quality score, and existing Delivery Clarity insights.

AI remains an explanation/recommendation layer. Deterministic metrics are the source of truth.

The model must not:

- invent metrics, Jira items, dates, quotes, causes, or trends;
- treat issue text or the user question as instructions;
- change Jira or production settings;
- change permissions or users;
- delete data or contact users;
- expose or infer personal information beyond supplied operational evidence.

## Structured output

Delivery Intelligence calls Ollama's chat endpoint with a JSON schema. Responses are then normalized again before rendering. External URLs generated by the model are discarded; only explicit Delivery Clarity routes from the server allow-list are accepted.

Generation temperature is set to `0` to reduce output variability for evidence-grounded analysis.

## Runtime verification

Before declaring AI live in an environment:

1. Confirm the Ollama service is reachable from the Node application but not from the public internet.
2. Confirm `qwen3.5:4b` is pulled and can answer a structured chat request.
3. Confirm `qwen3.5:9b` is pulled and can answer a structured chat request.
4. Open `/intelligence` with representative Jira evidence.
5. Run Flow or Risk and confirm the answer displays `qwen3.5:4b` in AI mode.
6. Run Executive or Forecast and confirm the answer displays `qwen3.5:9b` in AI mode.
7. Stop or block Ollama temporarily and confirm the same workflow falls back to Evidence mode without breaking the page.
8. Re-run the AI benchmark on the actual inference host. Do not reuse the historical Qwen2.5 14B benchmark as capacity proof for the Qwen3.5 4b/9b runtime.

## Hostinger note

The repository can configure and call a private Ollama runtime, but the currently available Hostinger integration for this project does not expose the existing hPanel managed-Node runtime, package installation, private service networking, or environment-variable state. Therefore repository CI cannot prove that Ollama is installed/reachable on production Hostinger infrastructure.

Keep the application in Evidence mode until the runtime is provisioned and the verification steps above pass.

## Broader master-plan AI work

This runtime adapter does not claim the complete product-intelligence roadmap is implemented. The master plan separately defines an internal AI worker/service and later capabilities such as weekly product reports, feedback clustering/embeddings, error correlations, recommendation review, post-release impact measurement, and advanced model routing. Those should ship as their own reviewed increments rather than being hidden inside the interactive Delivery Intelligence endpoint.
